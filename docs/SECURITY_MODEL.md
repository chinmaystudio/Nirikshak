# NIRIKSHAK — Security model

The database enforces every access rule. The frontend and backend add usability and early validation, but nothing they do can widen what a user is allowed to read or write.

## Identities and roles

| Role | Organisation type | Can |
| :--- | :--- | :--- |
| `citizen` | none | Read public projects; file and follow their own complaints; escalate, reopen, confirm resolution, give feedback |
| `government_engineer`, `project_officer` | government | Read and write their organisation's projects, tenders, progress reviews, complaints; sit on evaluation committees |
| `chief_engineer` | government | As above, plus set evaluation committees and award contracts |
| `government_admin` | government | As above, plus approve access requests, transfer project ownership, reset colleagues' two-step verification |
| `auditor` | government | Read-only access to their organisation's data and the audit log |
| `contractor_*` | contractor | Bid on public tenders; work only on projects assigned to their organisation; upload evidence to their own storage folder |
| Oversight members | government org with `is_oversight = true` | **Read** every organisation's projects, tenders, contracts and progress; never write outside their own organisation |

A user has at most one active organisation membership (unique index, migration 040).

## Registration and approval

1. Applicants register through the backend (`POST /api/auth/register`). Supabase sends a confirmation email; the account cannot sign in until it is confirmed.
2. Government applicants must use an official email domain (`GOV_EMAIL_DOMAINS` in the backend; `platform_settings.government_email_domains` in the database).
3. A government or contractor registration creates a **pending access request**, not a role.
4. An administrator approves it. The database refuses self-approval, unconfirmed emails, non-official domains for government roles, and role/organisation-type mismatches (migration 044). Every membership change is written to the audit log.

## Two-step verification (MFA)

- Government and contractor users enrol an authenticator app (TOTP) on first sign-in and enter a code at every sign-in.
- A password-only session has `aal = aal1`. Writes by government/contractor users require `aal2`:
  - **database:** restrictive RLS policies on every core table, plus wrappers on every privileged workflow function (migration 043);
  - **storage:** upload policies require it (migration 045);
  - **backend:** `requireMfa` on write routes.
- Lost authenticator: another administrator of the same organisation calls `POST /api/auth/mfa/reset` (see the runbook).

## Tenancy

Every project has an owning government organisation and every tender an issuing organisation (`NOT NULL`, migration 041). Officers see and change only their own organisation's records; oversight organisations read across organisations. `transfer_project_ownership()` moves a project to another authority and is audited.

## Procurement integrity (migration 042)

- **Sealed bids.** Officers cannot read any bid row until the bids are opened. Before that they see only the number of bids (`get_tender_bid_counts`, `get_tender_bid_summary`).
- **Committee.** A government admin or chief engineer of the issuing organisation names the evaluation committee: active officers of that organisation, not auditors. The committee is frozen once bids are opened.
- **Two-key opening.** After the bid due date, at least `min_opening_members` (default 2) committee members must each approve the opening.
- **Committee evaluation.** Each member scores each bid separately. The bid's scores are the committee average, and the combined score is `technical_weight × technical + (1 − technical_weight) × financial`, with the weight set per tender (default 0.7).
- **Award.** Only a government admin or chief engineer can award, and only after at least `min_evaluators` committee evaluations of the chosen bid.
- **Audit.** Bid amounts are removed from audit rows and replaced by a SHA-256 commitment, so the audit trail cannot be used to read sealed bids.

## Complaints

- Complaints are filed through the backend, which validates and sanitises them. Bot protection (Turnstile) applies when configured. Reference numbers are generated by the database: a sequence number plus a random suffix.
- Clients cannot write the status history directly. A database trigger logs every status change with the real actor; citizens use `citizen_complaint_action()` and officers use `update_complaint_status()`.
- Public tracking by reference number shows only status transitions and dates, never notes or personal details.
- Evidence files are stored privately under the complainant's own folder. Anonymous complaints cannot attach files.

## Personal data

- Profiles (name, phone) are visible only to the user themself, members of the same organisation, and government officers. Anonymous visitors cannot read them.
- Import and staging tables are accessible only to the service role.
- The AI context is stripped of credentials, personal data and bid contents before it is sent. Requests ask OpenRouter for zero-data-retention providers that do not collect data, and free model endpoints are refused by default.

## Audit log

`audit_logs` is append-only: clients cannot write to it, and an `UPDATE`/`DELETE` trigger blocks changes even for the database owner. Rows come from security-definer functions, triggers and the backend service role.

## Transport and browser

The frontend is served with a strict Content-Security-Policy, HSTS, `frame-ancestors 'none'`, `nosniff` and a restrictive Permissions-Policy (`frontend/public/_headers`). The API sets equivalent headers, allows CORS only for configured origins, limits request bodies, rate-limits by client IP (shared through Redis when configured), and never returns internal errors to clients.

## Verification

`backend/supabase/test/10_rls_security_tests.sql` checks every rule above as each role (78 checks). CI runs it on every change after rebuilding the schema from the migrations. To check the live database without changing anything, run `backend/supabase/test/audit_live_policies.sql` in the Supabase SQL editor.
